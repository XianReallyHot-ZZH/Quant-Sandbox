# ADR-0003: 保留双回测引擎,以对账桥显式管理口径差异

- 状态:Accepted(2026-09-01)
- 关联:ADR-0002;报告 §3.5、§3.6、§8.5 #1、§8.6

## 背景

参照物有两套回测引擎、两种 Sharpe 口径:事件引擎(Decimal 订单意图、挂单/限价/止损语义、风控前置)与滚动引擎(float 信号驱动 bar 循环、异步生成器、指标预计算),靠 `bridge.compare_engines()` 对账。报告判定双引擎是历史融合产物、非设计目标,风险清单第 1 条建议复现时「只做一套」(§8.5 #1)。

## 决策

**保留双引擎并复刻对账桥**——与报告建议相反,经权衡后刻意选择:

1. 事件引擎承担:M1 教学回测(PRD 合同的验收对象,§4.2 路径 A)、Decimal 订单语义、DSL 策略编译落点。
2. 滚动引擎承担:全部审计(PBO/DSR/CPCV/robustness)、walk-forward、30 策略族——即**审计主引擎**。
3. `compare_engines()` 对账作为滚动引擎落地后的一节**正式课**,不做选修:两套口径为何不可直接比较、如何对账,是理解回测系统语义的必修内容。
4. 报告中「只做一套」的建议被否决的理由:该建议服务「工具优先」目的;在「学习优先」(ADR-0001)下,双引擎的对账张力本身是教材。

## 后果

- 必须从第一天就写明:两套 Sharpe 口径不可直接比较(逐 bar 权益收益 vs 逐笔交易 PnL,§3.6),payload 里口径字段不可共用命名。
- 多付出 bridge 模块 + 对账测试的成本;换来对「回测引擎语义分层」的完整理解。
- 若未来发现维护成本失控,退化路径是:冻结事件引擎为只读教学件,主序继续——本 ADR 届时重开。
